# Мониторинг Odyssey

Мониторинг использует Prometheus как источник всех метрик Grafana. События продукта хранятся в существующей PostgreSQL; сервис library раз в 15 минут рассчитывает согласованный снимок. Опрос /metrics не выполняет SQL. Сбор начинается с применения 011_observability.sql; отсутствующая история не восстанавливается предположениями.

## Доступ

Основной адрес: https://77.91.114.154/grafana/. SSH-туннель для входа не нужен: открыть ссылку и авторизоваться в Grafana. Анонимный доступ и самостоятельная регистрация отключены. Пользователь по умолчанию admin; пароль хранится на сервере в /home/e.drobyazko/r-a/.monitoring-secrets/grafana_admin_password. Пароль не добавлять в репозиторий или общий лог.

HTTPS обслуживает grafana-proxy (Caddy) на TCP/UDP 443. Сертификат Let's Encrypt выпущен на IP-адрес; Caddy автоматически получает и продлевает его, сохраняя ключи и сертификаты в grafana_proxy_data. Проверка владения IP использует TLS-ALPN-01 через TCP 443. Порт 80 продолжает обслуживать существующий фронтенд.

Публичный адрес задаётся GRAFANA_PUBLIC_HOST. При изменении адреса обновить также URL проверки в prometheus.yml и alerts.yml, пересоздать grafana/grafana-proxy и проверить выпуск сертификата. Для сертификата IP используется профиль shortlived; остаток менее суток вызывает алерт. Документация: [сертификаты IP Let's Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability/), [автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).

Технический HTTP-порт Grafana остаётся привязан к 127.0.0.1:3001 сервера (GRAFANA_PORT), наружу он не публикуется. После включения Secure cookies браузерный вход следует выполнять через основной HTTPS-адрес.

Получить пароль в своей SSH-сессии на сервере:

```bash
sudo cat /home/e.drobyazko/r-a/.monitoring-secrets/grafana_admin_password
```

В Grafana доступны пять дашбордов:

- «Odyssey · Общее состояние»: аудитория, удержание, доступность, активные алерты.
- «Odyssey · Продукт и воронки»: активация, использование функций, BRR, конверсии и обратная связь.
- «Odyssey · Надёжность приложения»: HTTP, фактические итоги SSE, очереди, кэш и свежесть данных.
- «Odyssey · LLM и расходы»: попытки, токены, сообщённая стоимость и полнота отчётов.
- «Odyssey · Инфраструктура»: VPS, контейнеры, PostgreSQL, PgBouncer, Redis и MinIO.

Prometheus, Alertmanager и экспортеры не публикуются наружу. Их данные доступны через авторизованную Grafana. Для просмотра алертов подключён datasource Alertmanager; состояние firing также видно на обзорном дашборде.

## Определения продуктовых метрик

Учитываются авторизованные пользователи. Активность — запуск исследовательского действия, просмотр готового результата, открытие проекта или статьи, сохранение статьи либо создание заметки. Обновление токена, автоматическое обновление ленты и фоновая подготовка русских описаний активностью не считаются. DAU/WAU/MAU — скользящие окна 1/7/30 суток, а не календарные месяцы.

| Показатель | Расчёт |
| --- | --- |
| Активация | Доля зарегистрированных после начала сбора пользователей, увидевших готовый результат за первые 7 суток. Только пользователи с полным 7-дневным окном; последние 30 суток зрелых регистраций. |
| Время до ценности | Медиана и p90 от регистрации до первого просмотренного результата среди активированных пользователей той же когорты. |
| D7 / D30 | Возврат ровно в 7-й / 30-й календарный день UTC после регистрации. Последние 30 полностью наблюдавшихся дневных когорт, зарегистрированных после начала сбора. |
| W1 / W2 / W4 | Возврат в дни 1–7 / 8–14 / 22–28 после регистрации; зрелые когорты, UTC. |
| BRR7 / BRR30 | Доля проектов с содержательным действием в другой день UTC в течение 7/30 суток после создания. Последние 30 суток зрелых проектов, созданных после начала сбора. |
| Активация проекта | Доля проектов с сохранением статьи, заметкой или запуском действия за первые 7 суток; зрелые проекты. |
| Использования функций | Число событий result_viewed за 30 суток: готовый результат действительно появился в видимой области активной вкладки. Повторный просмотр того же результата в одной аналитической сессии дедуплицируется. |
| Feature adoption | Пользователи с просмотренным результатом функции / MAU. |
| Использований на пользователя | Просмотры результатов функции / MAU за 30 суток. Медиана и p90 распределения включают активных пользователей с нулём использований функции. |
| Конверсии поиска | Завершённые search / deep_research с полным 7-дневным окном, после которых открыли или сохранили статью с атрибуцией к тому же действию. Открытие и сохранение независимы: сохранить можно прямо из ответа. |
| Полезность | Доля положительных среди оставленных оценок. Рядом показывается покрытие оценками; это самооценка, а не объективная проверка качества. |
| Дальнейшие действия | Копирование ответа, сохранение статьи, создание заметки. Это сигналы использования, а не доказательство успешного решения задачи. |

Проект — пользовательская корневая папка. Вложенные папки относятся к её корню, системные папки исключены. Удаление проекта не удаляет его из знаменателя; удаление пользователя удаляет его события и историю проектов.

Аналитическая сессия заканчивается после 30 минут бездействия. Она отделена от сессии авторизации. Клиент передаёт время события; сервер принимает не старше 24 часов и не более 2 минут в будущем. Поздние события могут корректировать снимки.

При нулевом знаменателе Grafana показывает «Нет данных», а не 0% успеха/удержания. D7/W1 и активация требуют минимум недели наблюдений, D30 — полного 30-го дня. Наличие регистрации до начала наблюдения не создаёт достоверную историческую когорту.

## Технические метрики

- ra_http_*: частота, коды ответа, активные запросы, задержки. Route — зарегистрированный шаблон; произвольные URL и query не становятся метками.
- ra_action_*: фактический итог попытки. SSE error или обрыв без done считается ошибкой даже при HTTP 200; отмена клиента и ожидание summary 409/425 выделены отдельно. Первая порция содержимого исключает progress.
- ra_llm_*: обращения к провайдеру, ошибки/отмены, HTTP-коды, длительности, токены и стоимость. Повторная попытка — отдельный вызов провайдера.
- ra_summary_source_results_total: успешные POST-ответы обзора по наличию полного текста/только аннотации и попаданию в кэш. Чтение уже сохранённого обзора через GET учитывается продуктовым просмотром, но не POST-метрикой генерации.
- ra_queue_*, ra_job_*, ra_paper_pipeline_*: Asynq, ожидание PDF, попытки обработки и результаты этапов.
- ra_cache_*, ra_feed_*: кэш и время публикации подготовленной ленты.
- ra_db_pool_*: соединения pgx, ожидание и отмены.
- up, probe_*, node_*, container_*, pg_*, pgbouncer_*, redis_*, minio_*: источники метрик и зависимости.

Стоимость берётся только из поля cost ответа провайдера. Отсутствующий usage/cost показывается как отсутствие отчёта, а не бесплатный запрос. Оценки по публичным прайсам не добавляются. Для финансовой сверки нужен отдельный отчёт провайдера.

Продуктовые ra_product_* — готовые gauges, к ним нельзя применять rate()/increase(). Для технических counters использовать rate()/increase(), учитывая, что первый запрос до первого опроса Prometheus и рестарты ограничивают точность коротких окон.

## Установка и обновление

Все команды выполнять в /home/e.drobyazko/r-a с нужными правами. Перед первым обновлением сохранить исходники, текущие ID образов и pg_dump. Основной .env сохраняется без изменений.

```bash
sudo python3 monitoring/bootstrap.py
sudo docker compose --env-file .env --env-file .env.monitoring -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.monitoring.yml config --quiet
sudo docker compose --env-file .env --env-file .env.monitoring -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.monitoring.yml run --rm migrate
sudo docker compose --env-file .env --env-file .env.monitoring -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.monitoring.yml build
sudo docker compose --env-file .env --env-file .env.monitoring -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.monitoring.yml up -d
```

bootstrap.py создаёт роль ra_monitor с pg_monitor без выдачи доступа к прикладным таблицам, приватные секреты и .env.monitoring. Повторный запуск сохраняет секреты и операторские настройки. При существующей роли без сохранённого пароля останавливается, не меняя пароль.

Использовать все три Compose-файла при последующих обновлениях. Не запускать down -v: это удаляет данные. В случае отката приложения аддитивные таблицы аналитики можно оставить; старый код их не использует.

Prometheus хранит до 90 дней или 15 GB; лимит места может сократить доступную историю. Продуктовые события в PostgreSQL автоматически не удаляются. Следить за ростом таблицы и резервными копиями; срок хранения согласовать отдельно до включения очистки, чтобы не обрезать зрелые когорты.

Изменения дашбордов вносить в monitoring/generate_dashboards.py, затем запускать:

```bash
python3 monitoring/generate_dashboards.py
```

Provisioning перезаписывает ручные изменения. Образы закреплены в docker-compose.monitoring.yml.

## Алерты и эксплуатационные ограничения

Настроены проверки недоступности endpoint/метрик, HTTP и SSE ошибок, очереди, свежести ленты и продуктовых агрегатов, записи событий, свободного диска/RAM и ошибок авторизации/баланса LLM. Состояния доступны в Grafana и Alertmanager. Внешний канал пока не настроен; уведомления в Telegram/email не отправляются.

Для подключения доставки нужны согласованные получатель и реквизиты канала. Настройки receiver добавлять в закрытый конфиг/секреты, не публиковать токены в репозитории.

Опциональный LLM_DAILY_BUDGET_USD в .env.monitoring задаёт положительный лимит сообщённых расходов за скользящие 24 часа. После изменения пересоздать library. Если значение отсутствует, бюджетный алерт отключён. Покрытие cost может быть неполным.

Blackbox запущен на том же VPS: обнаруживает проблемы HTTP/сервисов, но не может отправить сигнал при потере всего VPS. Для этого нужен отдельный внешний узел/сервис проверки; он пока не подключён.

Prometheus хранит технические ряды на своём томе; перезапуск не стирает их. Продуктовый агрегатор сохраняет последний успешный снимок при ошибке и повторяет расчёт через 30 секунд. На экране нужно учитывать давность пересчёта.

## Конфиденциальность и проверка

В метках Prometheus нет user_id, email, project_id, paper_id, IP, запросов, ответов или сырых URL. PostgreSQL хранит только метаданные событий с авторизованным user_id для когорт. Клиент не может назначить чужой user_id или подменить серверные event_type. Приём ограничен 20 событиями/32 KiB за запрос и 60 пакетами в минуту на пользователя.

VITE_ENABLE_ANALYTICS=false выключает клиентские события в сборке. В dev они по умолчанию выключены; для проверки включаются VITE_ANALYTICS_IN_DEV=true. Серверные технические метрики и авторизованные API-действия наблюдаются независимо.

Проверки реализации: Go-тесты SSE и когорт на изолированной PostgreSQL, сборка TypeScript/Vite, Python-тесты маршрутов и usage, promtool, amtool, Compose config. После выпуска дополнительно проверить /api/v1/targets и /api/v1/rules у Prometheus, provisioning Grafana и отсутствие scrape errors. Метрики функций появляются после настоящих вызовов; отсутствие таких рядов до первого использования нормально.
