# Настройки приложения и прямые LLM API

Все настройки объявлены обычными переменными в корневом
[`settings.py`](../settings.py). Значения по умолчанию указаны прямо в коде,
переменные окружения переопределяют их через `os.getenv`:

```python
OPENAI_BASE_URL = os.getenv("OPENAI_BASE_URL", "https://api.openai.com/v1")
LLM_MODEL = os.getenv("LLM_MODEL", "gpt-6.1-terra")
SUMMARY_LLM_MODEL = os.getenv("SUMMARY_LLM_MODEL", LLM_MODEL)
```

Python-сервисы используют `import settings` и обращаются к конкретным переменным,
например `settings.LLM_MODEL`. Другие настройки по умолчанию могут ссылаться на
уже объявленные переменные, как `SUMMARY_LLM_MODEL` в примере.

Пустое значение env тоже считается явным переопределением. Настройки читаются
при запуске: после изменения файла или env сервис нужно перезапустить.
После изменения значений по умолчанию в Docker образы нужно пересобрать.

Go при запуске читает значения из того же `settings.py` через `python3`.
Vite использует его при запуске или сборке, передавая env из `frontend/.env`.
Во фронтенд попадают только публичные параметры `VITE_*`; серверные настройки
и секреты не передаются. Python 3 нужен для Go-сервисов и сборки фронтенда;
в Dockerfile эта зависимость уже установлена.

Docker Compose читает `.env` через `env_file`. Команды `go run` и обычный запуск
Python читают переменные процесса; `.env` автоматически не исполняется.
Адреса БД, Redis, хранилища и внутренних сервисов внутри Docker задаёт Compose.

## Провайдеры и модели

| Назначение | Модель | Адрес | Ключ |
|---|---|---|---|
| Чат и объяснение фрагментов | `LLM_MODEL` | `LLM_BASE_URL` → `OPENAI_BASE_URL` | `LLM_API_KEY` → `OPENAI_API_KEY` |
| Обзор статьи | `SUMMARY_LLM_MODEL` → `LLM_MODEL` | как у чата | как у чата |
| Веб-поиск | `WEBSEARCH_LLM_MODEL` → `LLM_MODEL` | `WEBSEARCH_LLM_BASE_URL` → `OPENAI_BASE_URL` | `WEBSEARCH_LLM_API_KEY` → `OPENAI_API_KEY` |
| Глубокое исследование | `WEBSEARCH_DEEP_LLM_MODEL` → `LLM_MODEL` | как у веб-поиска | как у веб-поиска |
| Перевод фрагментов | `TRANSLATION_LLM_MODEL` | `TRANSLATION_BASE_URL` → `OPENROUTER_BASE_URL` | `TRANSLATION_API_KEY` → `OPENROUTER_API_KEY` |
| Описания ленты | `FEED_TRANSLATION_MODEL` → `TRANSLATION_LLM_MODEL` | `FEED_TRANSLATION_BASE_URL` → `TRANSLATION_BASE_URL` | `FEED_TRANSLATION_API_KEY` → `TRANSLATION_API_KEY` |

По умолчанию OpenAI использует `https://api.openai.com/v1`, OpenRouter —
`https://openrouter.ai/api/v1`. Все функции OpenAI по умолчанию используют
`gpt-6.1-terra`. Чат, объяснение фрагментов, обзор и обычный веб-поиск используют
`reasoning.effort=medium`, а глубокое исследование — `max`. У глубокого исследования
собственное значение по умолчанию, независимое от `LLM_REASONING_EFFORT`.
Модель и уровень рассуждений можно
переопределить через env. Пустая модель даёт ошибку до обращения к провайдеру. Для OpenAI указывают его
собственный идентификатор модели, без префикса OpenRouter `openai/`.
Gemma сохранена: `google/gemma-4-26b-a4b-it`.

Ключи хранить в env, а не в общем файле настроек. Ключи ProxyAPI не подходят
для прямых API. При обновлении существующего `.env` нужно убрать из него старые адреса ProxyAPI, модели Perplexity и `LLM_PROVIDER=openai_compatible`.
Провайдер основных функций теперь `LLM_PROVIDER=openai`. Старые значения в env
имеют приоритет и не будут молча заменены настройками из файла.

Для выбора моделей достаточно изменить `LLM_MODEL` в файле или env. Отдельные
модели функций переопределяются параметрами из таблицы. `LLM_MODELS` задаёт
разрешённый список в переключателе чата: `id|Название,id2|Название2`.

## Поиск и глубокое исследование

Оба режима используют `/v1/responses` и встроенный инструмент `web_search`.
Поиск обязателен, домены берутся из `WEBSEARCH_DOMAINS`; пустая строка отключает
ограничение доменов. У режимов отдельные настройки усилия рассуждений,
числа вызовов инструментов, длины ответа и общего таймаута. Эти бюджеты
ограничивают работу модели, но не являются точным ограничением стоимости.

Лимиты `max_output_tokens` включают рассуждения модели и итоговый текст.
По умолчанию чат и обычный веб-поиск получают до 16 000 токенов, обзор — до
32 000, глубокое исследование — до 64 000. Для глубокого исследования установлен
общий таймаут 30 минут. Перевод Gemma использует прежние параметры и отдельные
лимиты OpenRouter.

Deep research запускается с `background=true`, `stream=true` и `store=true`.
Python восстанавливает оборванный поток OpenAI по идентификатору ответа и
`sequence_number`, не создавая новый запрос. В интерфейс передаются только доступные
пользователю сводки рассуждений и события поиска; внутренние рассуждения не выводятся.
Цитаты из аннотаций API превращаются в кликабельные ссылки в итоговом тексте.

Миграция `013_search_runs.sql` добавляет состояние исследования и идентификатор
OpenAI. Отключение браузера не прерывает сохранение отчёта. После перезапуска
backend открытие чата проверяет сохранённый ответ OpenAI и сохраняет завершённый
отчёт. Одновременное завершение потока и восстановление не создаёт дубликатов.
Удаление чата останавливает незавершённую фоновую задачу.

В потоке есть событие `replace`: итоговый текст заменяет накопленные фрагменты,
чтобы аннотации цитат стали ссылками. События `delta`, `progress`,
`source_progress`, `sources`, `done` и `error` сохранены.

## Просмотр действующих настроек

Из корня проекта:

```bash
python3 settings.py
```

Команда показывает настройки текущего процесса. Значения ключей, паролей,
токенов и подключений к БД скрыты. Модели, адреса API и лимиты видны.
Чтобы увидеть окружение из `.env` внутри локального Docker:

```bash
docker compose run --rm --no-deps websearch python settings.py
```

`/health` поискового сервиса также показывает провайдера, адрес, модели и
признак наличия настроек, без API-ключей. Эта проверка не вызывает модель.

## Локальная проверка

```bash
cd backend
go test ./...
```

Python-сервисы используют одинаковое имя пакета `app`, поэтому их тесты
запускаются отдельно из корня проекта:

```bash
PYTHONPATH=services/websearch:. python3 -m pytest services/websearch/tests tests
PYTHONPATH=services/parser:. python3 -m pytest services/parser/tests
```

Интеграционные тесты исследования используют `SEARCHAPI_TEST_DATABASE_URL` и
создают отдельные временные схемы. Не направлять их в рабочую БД. Проверка
транспорта выполняется локальными тестовыми HTTP-серверами; реальное качество
ответов проверяется отдельно с настроенными ключами провайдеров.
